## I6: tick cada minuto y compuerta durable de consultas ITAD

El cron LOCAL ([wrangler.local-integration.jsonc](../wrangler.local-integration.jsonc))
dispara `scheduled` cada minuto (`* * * * *`) y la composicion usa `runTick`
([src/bridge.ts](../src/bridge.ts)). La configuracion de produccion versionada
sigue siendo el mock por defecto ([wrangler.jsonc](../wrangler.jsonc)), sin
cron, D1 ni despliegue.

- Consultas oficiales a ITAD (lectura/descifrado del sobre OAuth, refresh,
  lista y detalles): solo cuando la compuerta durable `poll_gate` de D1
  (migracion [0004](../migrations/0004_i6_poll_gate.sql)) esta vencida y la
  invocacion la reserva con CAS (`owner`, `claim_version`, caducidad 120 s).
  Intervalo minimo 5 min (`pollIntervalMs` 300000): al terminar se programa
  `next_poll_at = inicio + 300 s`. Un tick retrasado puede demorar la siguiente
  consulta, pero no adelantarla. Nunca se usa memoria del isolate como compuerta.
- Entrega de partes ya persistidas: en CADA tick (cada minuto), con los mismos
  limites, throttle durable y reservas. Un tick no vencido no lee OAuth, no
  refresca y no hace GET a ITAD (`poll: not_due`, `calls` a cero salvo envios).
- Concurrencia: solo una invocacion obtiene la compuerta; las demas devuelven
  `poll_busy`/`not_due` sin llamadas externas a ITAD y siguen drenando con las
  reservas de parte y el throttle compartidos. Un propietario caido se
  sustituye cuando caduca su reserva (120 s); puede repetirse entonces un GET de
  lista o detalle (lectura, sin envios). Un propietario caducado no renueva ni
  cierra la compuerta (`poll_lease_lost`).
- Duracion: antes de cada llamada externa (refresh, cada GET de lista, cada
  reserva de detalle) se comprueba la propiedad y se renueva la reserva si quedan
  menos de 60 s. Cada GET tiene timeout de 10 s y como mucho hay 1 refresh +
  2 listas (401) + 3 detalles, por lo que el peor caso (~60 s) cabe en 120 s; si
  se pierde la reserva no se consultan mas detalles y estos quedan pendientes.
- 429 de ITAD/OAuth (lista, detalle o refresh): `next_poll_at` nunca es anterior
  a `retry_after` (60 s si falta); la entrega sigue cada minuto.
- `refresh_busy`: se libera la compuerta sin mover `next_poll_at` (reintento en
  el siguiente tick). Fallo de baseline/lista: `ok` falso y nuevo intento en el
  siguiente hueco de 5 min, nunca como exito.
- Lectura/escritura de la compuerta fallida o fila ausente: `poll:
  gate_unavailable`, errores `poll_gate_unavailable` + categoria
  (`storage_state` si falta la fila), `ok` falso y `scheduled` lanza; no se
  consulta ITAD y la entrega continua. Fallo al cerrarla: `poll_gate_not_persisted`
  (la reserva caduca a los 120 s).
- Con `oauth_reauth` no se toca la compuerta (`pollGate: skipped`).
- Detalles: solo en ticks vencidos, hasta 3 por consulta, en orden; los que
  exceden esperan al siguiente tick vencido (nunca se saltan). El reintento
  efectivo de un detalle fallido pasa a ser ~5 min (5 intentos ~25 min).
- `runCycle` se conserva como API independiente sin compuerta (pruebas y uso
  puntual); `scheduled` nunca la usa.
- `local-integration` lee ademas `oauthSessionVersion()` (columna D1, sin
  descifrar) en cada tick para sembrar la simulacion; produccion no.

Resumen por tick (sanitizado): `pollGate` (`claimed`, `not_due`, `busy`,
`unavailable`, `skipped`, `bypassed`), `nextPollInSeconds`, `calls`
(`oauthRefresh`, `itadList`, `itadDetail`, `telegramSend`) y `queue`
(`pendingParts`, `oldestOpenAgeSeconds`...).

## Flujo de cada invocacion `scheduled`

Pasos de una consulta (en `runTick` solo con la compuerta reservada; la entrega
del paso 5 corre en todos los ticks):

1. Lee los indicadores durables (`bridge_flags`). Con `oauth_reauth` no consulta
   ITAD, pero sigue entregando el trabajo ya persistido. Si la lectura falla
   (I6) no se interpreta como "sin indicadores": la ejecucion no consulta ni
   envia (`deliveryStop: flags_unavailable`, error `flags_unavailable`, `ok`
   falso) y el trabajo pendiente queda en D1 para la siguiente ejecucion.
2. Lee y descifra el sobre AES-GCM de D1 en cada invocacion (nunca se cachea
   entre invocaciones). Si el token expira en menos de 24 h, reserva el refresh
   con CAS/version (I4); otra ejecucion concurrente usa el token vigente o se
   detiene con `refresh_busy`. Tras el refresh guarda el par rotado con CAS.
   - `invalid_grant`/`invalid_client`/`unauthorized_client`/`invalid_scope`:
     indicador `oauth_reauth` visible.
   - Error transitorio de refresh: libera la reserva y usa el token aun valido.
     Si la respuesta se perdio tras rotar en ITAD, el siguiente refresh recibe
     `invalid_grant` y se marca `oauth_reauth`.
   - Si el par nuevo no se puede persistir: `oauth_reauth` con
     `refresh_not_persisted`; el token nuevo solo se usa en memoria en esa
     ejecucion y el ciclo termina con error.
   - 401 en la lista: un refresh forzado y un reintento; un segundo 401 marca
     `oauth_reauth` con `access_rejected`.
3. `GET /notifications/v1`. Primera vez: baseline atomico de todos los IDs, sin
   detalle ni envios. Despues: IDs nuevos (aunque esten leidos) en orden de
   `timestamp` y despues `id`. No se filtran leidos ni se llama a read/read-all.
4. Detalle: hasta `maxDetailsPerRun` avisos pendientes en orden de descubrimiento;
   antes de cada consulta se reserva el detalle en D1 (I6, migracion 0003:
   propietario, version y caducidad de 120 s con CAS, igual que las partes). La
   reserva vuelve a comprobar en la misma sentencia que no este bloqueado y que
   su espera haya vencido; las ejecuciones solapadas que no la obtienen lo
   saltan sin consultar ni gastar intento. Valida, formatea con
   `formatNotification` (todos los juegos y ofertas, sin precios consultados
   aparte) y guarda detalle+partes en un batch protegido por la reserva. 429
   aplaza sin contar intento y para la fase; 401 libera la reserva sin contar y
   para la fase; URL imposible de formatear se bloquea como `format_rejected`;
   otros fallos cuentan intento con espera de `detailBackoffMs` y se bloquean
   tras 5 intentos totales. Registrar el fallo libera la reserva.
5. Entrega: partes en orden `planned_seq` y `part_index`, cabeza de linea por
   aviso (no se mezclan partes ni avisos). Antes de cada envio se reserva el hueco
   del throttle global durable (`chat_throttle`, CAS compartido por ejecuciones
   solapadas, >= 1000 ms) y despues la reserva de parte de 120 s.
6. Confirmacion solo con HTTP 2xx, `ok: true`, `result.message_id` entero >= 1,
   `result.chat.id` igual al chat configurado y `chat.type` `private`. Se guarda
   el recibo `telegram_message_id:N` con CAS de la reserva.
7. Resumen sanitizado en una linea JSON (contadores/categorias). Si `ok` es
   falso, `scheduled` lanza `bridge_cycle_failed:<categorias>`: nunca exito
   silencioso.

## Errores de Telegram

Rich usa el mismo cliente, recibos y throttle. Ante **400 con imágenes**, un único
fallback sin imágenes (no entrega confirmada del primer intento); si persiste
400, la parte queda bloqueada como `rejected_bad_request`. No se interpretan
descripciones ni se reintenta automáticamente un envío ambiguo sin imágenes.

| Categoria | Casos | Accion |
| --- | --- | --- |
| `rate_limit` | 429 | `parameters.retry_after` (30 s si falta/invalido) persistido en la parte y en el throttle global; no cuenta intento; sin dormir con la reserva; fin de entrega en esa ejecucion. |
| `transient` | red, timeout 10 s, 5xx | Intento contado, espera 30 s x intentos; al 5o queda `transient_exhausted` (bloqueado recuperable). |
| `destination` | 401, 403, 404, `migrate_to_chat_id` | Parte sigue pendiente sin contar; indicador `delivery_halt`; no se sigue la migracion. |
| `unverified` | 2xx sin JSON/forma, `message_id` < 1, otro chat, chat no privado | Parte bloqueada SIN reintento automatico (pudo enviarse); otro chat/no privado tambien activa `delivery_halt`. |
| `rejected` | 400, otros 4xx, redirecciones | Parte bloqueada; el aviso se salta y los siguientes avanzan. |

Un 400 puede ser "chat not found"; no se interpretan descripciones, asi que solo
se bloquea esa parte. Un aviso con una parte bloqueada no envia sus partes
restantes; tras recuperarlo puede llegar despues de avisos mas nuevos (cada parte
lleva `Aviso ITAD <id> · parte N/M`).

## Garantias y ventana de duplicados

No hay entrega exactamente una vez. Si Telegram acepta un mensaje y el recibo no
se guarda (fallo D1, reserva caducada), la parte sigue reservada hasta 120 s y
despues otra ejecucion puede reenviarla. Un propietario caducado no puede
confirmar ni liberar (CAS). Un `unverified` no se reenvia automaticamente.

Reservas de detalle (I6): un propietario caducado o sustituido no registra
fallos, no libera ni guarda el plan (`detail_lease_lost`). Si una ejecucion cae
tras consultar y antes de registrar el resultado, la reserva caduca a los 120 s
y otra ejecucion repite la consulta; ese intento no observado no se cuenta, por
lo que tras caidas repetidas puede haber mas de 5 consultas GET (nunca mas de 5
fallos registrados). Las consultas de detalle son lecturas y no generan envios.

## Limites provisionales (`PROVISIONAL_LIMITS` en src/bridge.ts)

`maxDetailsPerRun` 3, `maxSendsPerRun` 3, `sendIntervalMs` 1000,
`maxInlineWaitMs` 1500, `maxTransientAttempts` 5, `transientBackoffMs` 30000,
`maxDetailAttempts` 5, `detailBackoffMs` 60000, `refreshMarginMs` 24 h.
Nada se descarta: lo que excede el lote queda pendiente para la siguiente
ejecucion y el resumen informa `oldestOpenAgeSeconds`. Desde I6 la entrega
corre cada minuto (3 mensajes/min); un aviso de 20 partes tarda 7 ticks. No se
han medido CPU, duracion ni subrequests por invocacion en Cloudflare.
I6 anade `pollIntervalMs` 300000. La tolerancia de adelanto de 30 s se retiro:
el intervalo durable minimo es 300 s, sin adelantar consultas.
Solo se admite chat privado (id entero positivo); grupos/canales no estan
habilitados.

## Rich y bundles: persistencia, agenda y diagnóstico

La migración [0005](../migrations/0005_rich_bundles.sql) añade formato durable
(`rich_html` / texto anterior), IDs `bundle:<id>` y baseline/agenda separados
de bundles. Conserva la cola y recibos anteriores; redeploy con misma D1 no
repite baseline ni partes confirmadas. La deduplicación de bundles usa el ID:
un relanzamiento con el mismo ID no es nuevo.

Avisos oficiales siguen cada 5 min, tick de entrega cada 1 min. Bundles usan
`GET /bundles/v2` con API key opcional, **country=ES**, **mature=true**, intervalo
60 min tras chequeo resuelto. Primer chequeo pagina el feed activo y registra
baseline sin envíos (máximo provisional 10 páginas de 50; no completa baseline
parcial si se excede). Posteriores leen solo **50 recientes**, hasta 3 planes
por ejecución; un chequeo incompleto/fallido se vuelve a programar en 10 min
(429 puede aplazar). No hay recuperación completa garantizada tras parada larga.

No existe regla oficial de notificación de bundles: el feed se cruza con
Waitlist **al detectar** un ID nuevo. Los no coincidentes se registran vistos;
añadir después el juego a Waitlist no genera aviso retroactivo. En coincidencia,
se conservan todos los juegos y niveles, incluidos los que no coinciden.
Colección solo marca pertenencia, no excluye juegos.

Diseño Rich ajustado localmente: sin cabeceras resumen Waitlist/bundle ni pies
con IDs, fecha/estado leído del aviso o publicación del bundle. Conserva títulos,
banner opcional, todas las ofertas/juegos/niveles, precio actual, mínimo histórico
del juego, tiendas, cupones, marcas y enlaces/botones intactos. Se omiten
etiquetas DLC/paquete y contenido adulto, precios secundarios de tienda, precio
anterior, señal S, DRM/plataformas y publicación. La señal H/N se etiqueta
«Mínimo histórico»; el valor `historyLow` se muestra una sola vez por juego y
evita duplicar la etiqueta en una primera oferta H/N. Con `historyLow: null`,
la oferta H/N muestra solo la etiqueta. No se infiere el flag comparando precios.
Solo muestra caducidad, fija Madrid `hh:mm dd-mm-aaaa`.
El mínimo de tres meses no está integrado ni se infiere y queda pendiente.
Solo las multipartes llevan
`parte X/Y`, reservado en el presupuesto Rich sin truncar contenido.
No modifica el texto legado ni reescribe planes Rich ya persistidos: el ajuste
se aplica a planes nuevos y al preview; IDs, deduplicación y recibos no cambian.

Sesión antigua `notifications`: avisos funcionan sin banners. Reautorizar
`notifications wait_read coll_read` para banners/cruce/marcas. Sin API key:
`bundles.state=off`; con key sin `wait_read`: `scope_missing` y error
`bundles_scope_missing`, pero avisos/cola siguen su fase. Fallo de banners solo
quita decoración; fallo de Colección quita marcas (warnings, no filtro).

Resumen JSON sanitizado: `warnings` (`banners_<categoría>`,
`collection_<categoría>`), `errors` y `bundles` (`state`, `listed`,
`baselineRecorded`, `seen`, `planned`, `invalid`). Estados: `off`, `idle`,
`not_due`, `scope_missing`, `baseline_initialized`, `baseline_already_initialized`,
`checked`, `failed`. `calls` añade `itadWaitlistGames`, `itadCollection`,
`itadBundles` a `oauthRefresh`, `itadList`, `itadDetail`, `telegramSend`.
`telegramSend` cuenta intentos de parte, no prueba render ni cuenta necesariamente
los dos HTTP de un fallback 400. Revisar también `sent`, `deliveryStop`, `queue`
y edad/bloqueos: warnings no son una entrega perdida y `planned` no significa enviado.
No registrar HTML, respuestas, enlaces, API key ni tokens para diagnosticarlos.

CPU/cuotas Free, moneda real para ES, render Telegram y aviso natural con correo
desactivado siguen pendientes. No hay exactamente una vez: aceptación con ack
o persistencia perdida puede duplicar; `unverified` se bloquea para revisión.

## Operaciones de operador (solo D1 local)

Metodos del adaptador: `flags`, `clearFlag`, `requeueBlocked`,
`confirmBlockedPartManually`, `queueStatus`, `replaceOAuthTokensAfterReauthorization`
(este ultimo borra `oauth_reauth`). Para la D1 local de `dev:cron`:

```powershell
$d1 = 'npx wrangler d1 execute itad-local-integration --local --config wrangler.local-integration.jsonc --command'
# Ver indicadores y trabajo bloqueado
Invoke-Expression "$d1 `"SELECT flag_key, category, set_at FROM bridge_flags`""
Invoke-Expression "$d1 `"SELECT notification_id, part_index, blocked_category, attempts FROM delivery_parts WHERE blocked_category IS NOT NULL`""
# Reanudar tras corregir el destino
Invoke-Expression "$d1 `"DELETE FROM bridge_flags WHERE flag_key = 'delivery_halt'`""
# Reencolar partes/detalles bloqueados (equivale a requeueBlocked)
Invoke-Expression "$d1 `"UPDATE delivery_parts SET blocked_category = NULL, blocked_at = NULL, attempts = 0, next_attempt_at = 0 WHERE blocked_category IS NOT NULL AND status = 'pending'`""
Invoke-Expression "$d1 `"UPDATE notification_work SET detail_blocked = NULL, detail_attempts = 0, detail_next_at = 0 WHERE detail_blocked IS NOT NULL AND status = 'pending_detail'`""
```

Antes de reencolar un `unverified`, comprobar el chat: si el mensaje llego, usar
`confirmBlockedPartManually` (recibo `operator_manual:<ms>`) en lugar de reenviar.
Contra D1 remota estas operaciones requieren autorizacion y quedan para I6/I7.
Desde I7 existe `npm run oauth:operator` para provisioning/reautorizacion
OAuth remotos y recuperacion exacta de partes; requiere permisos y no se ha
ejecutado. La herramienta limita recuperacion a categorias ambiguas admitidas,
exige confirmacion explicita y no despeja `delivery_halt`.

## Correcciones de compatibilidad Workers

- `redirect: 'error'` no existe en workerd; ITAD y Telegram usan
  `redirect: 'manual'` y rechazan explicitamente cualquier 3xx (nunca siguen).
- El cifrado AES-GCM pasa vistas `Uint8Array` (Node rechazaba `DataView` al
  descifrar; workerd acepta ambas). El formato del sobre no cambia.

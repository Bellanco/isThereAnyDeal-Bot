# I4: almacenamiento local D1

Implementacion aislada; no conecta el cliente ITAD, OAuth, cron ni Telegram al
Worker principal. El acceso OAuth usado en pruebas es ficticio, local y nunca
sale del arnes. No se crearon bindings ni recursos remotos.

## Persistencia

[La migracion 0001](../migrations/0001_i4_storage.sql) crea:

- marcador unico de baseline y tabla de IDs conocidos con origen `baseline` o
  `new`;
- trabajo `pending_detail` que sobrevive a fallos de lectura/reinicio;
- detalle oficial completo, JSON de todas las partes y filas por parte;
- estado `pending`/`leased`/`confirmed`, titular, version CAS, vencimiento y
  recibo durable;
- sobre cifrado de tokens, version de sesion/clave, reserva de refresh y un
  registro unico de nonces AES-GCM utilizados.

`initializeBaseline` valida todos los IDs antes de ejecutar un unico `D1.batch`.
El marcador y el conjunto quedan en la misma transaccion; una excepcion revierte
ambos. Tras completarse, las llamadas siguientes no reemplazan ni amplian el
baseline. `discover` solo admite trabajo despues de ese marcador y conserva IDs
nuevos sin filtrar por `read`. IDs repetidos son idempotentes.

El caller debe invocar baseline solo despues de recibir y validar una lista
completa de ITAD. Un error HTTP, JSON, validacion o base de datos no se convierte
en lista vacia ni en baseline completado. No se asume paginacion/retencion API.
El uso de `json_each(?)` inserta el lote en una sola sentencia sin descartar
entradas; si un limite real de D1 impide guardarlo, el batch falla y no se marca
baseline. No hay topes locales de juegos, avisos o partes ni limpieza automatica.

El detalle y todas las partes se guardan en una operacion atomica. Fallar su
persistencia deja `pending_detail` recuperable; volver a presentar el mismo plan
es idempotente y un plan distinto no sustituye al primero. La reserva de cada
parte dura 120 segundos; titular, version, vencimiento y estado se comprueban
en la misma actualizacion CAS. Un trabajador vencido no puede confirmar ni
liberar una reserva reemplazada. Los recibos confirmados no se eliminan.

Esto persiste el plan y los recibos, pero no ofrece entrega exactamente una vez:
un servicio externo podria aceptar un mensaje mientras se pierde su respuesta
antes de guardar el recibo. La integracion y politica de reintentos corresponden
a I5. Sin retencion ni capacidad de produccion acordadas, las tablas pueden
crecer; no se borra informacion silenciosamente.

## OAuth cifrado

`D1Storage.create` valida e importa la clave externa antes de cualquier acceso
a D1. Acepta una clave AES de 32 bytes en Base64 y un identificador de version.
Cada sobre usa AES-GCM, nonce aleatorio de 96 bits, y AAD que autentica la
version del sobre, version de clave y version de sesion. `oauth_nonce_history`
impone unicidad duradera por nonce. En D1 solo quedan nonce, metadata autenticada
y ciphertext; access/refresh tokens no se almacenan en claro ni se escriben en
logs.

La clave real se introducira en una fase posterior como Workers secret, nunca
como variable versionada ni en D1. Cambiar clave/version invalida la lectura
anterior de forma cerrada. La rotacion planificada de refresh actualiza el
conjunto cifrado con CAS de version de sesion, titular, version de reserva y
expiracion. La reautorizacion explicita puede sustituir una sesion mediante CAS
e invalida reservas antiguas; no hay endpoint de reautorizacion en este paso.

ITAD ya se observo rotando tanto access como refresh tokens. Si la respuesta de
refresh se pierde, o si D1 falla despues de que ITAD haya invalidado el refresh
anterior, el token durable puede quedar obsoleto y requerir reautorizacion.
No se garantiza recuperacion automatica de una rotacion parcial. I4 no realiza
requests OAuth ni intenta refrescar.

## QA local

Comandos disponibles desde la raiz:

```powershell
npm run test:d1
npm run typecheck
npm test
```

`test:d1` ejecuta la migracion con Wrangler `--local` y solo contra el binding
local de [wrangler.d1-test.jsonc](../wrangler.d1-test.jsonc), luego arranca un
Worker QA en `127.0.0.1` con persistencia temporal y la elimina al terminar.
El proceso hereda solo variables de entorno de sistema necesarias; su HOME,
configuracion y persistencia se aíslan en la carpeta temporal. No hay
`--remote`, token Cloudflare heredado, secreto real, cuenta ITAD, Telegram ni
llamadas externas.
El arnes comprueba rollback de baseline/plan, baseline y pendientes tras
reinicio, idempotencia, detalle pendiente y retry, concurrencia/CAS, expiry,
recibos, ciphertext, clave invalida, tamper, rotacion OAuth y reautorizacion.
La suite Vitest y el typecheck se ejecutan por separado.

# I2: cliente ITAD y OAuth simulado

Implementado aisladamente, no conectado a Workers ni al receptor mock. Sin
dependencias nuevas, almacenamiento durable, baseline, cron o Telegram.
No se inicia OAuth ni un listener al importar/ejecutar las pruebas.

## Fuentes verificadas (2026-10-31)

- [Documentacion ITAD](https://docs.isthereanydeal.com):
  Authorization Code con PKCE, access token JWT de longitud variable,
  cabecera Authorization; 429 con cabecera Retry-After.
- [Definicion oficial](https://github.com/IsThereAnyDeal/API/blob/master/docs/docs.yaml):
  authorize `https://isthereanydeal.com/oauth/authorize/`;
  token y refresh `https://isthereanydeal.com/oauth/token/`.
- [GET lista](https://github.com/IsThereAnyDeal/API/blob/master/docs/routes/notifications/list.v1.yaml)
  y [GET detalle](https://github.com/IsThereAnyDeal/API/blob/master/docs/routes/notifications/waitlist.v1.yaml):
  permiso `notifications`, array de lista, detalle con query `id` UUID.
  No parametros de paginacion documentados; no llamar read/read-all.
- [Errores API](https://github.com/IsThereAnyDeal/API/blob/master/docs/defs/error-response.yaml):
  `status_code`, `reason_phrase`. No se publica el texto externo.
- [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749):
  secciones 2.3.1 (autenticacion cliente), 4.1.1/4.1.2 (authorize/callback),
  4.1.3 (intercambio), 5.1/5.2 (tokens/errores), 6 (refresh).
- [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636):
  PKCE S256 y ejemplo del apendice B usado en pruebas.
- [Guia de intercambio enlazada por ITAD](https://www.oauth.com/oauth2-servers/access-tokens/authorization-code-request/).

**Distincion importante:** ITAD documenta endpoints, PKCE y permiso, pero no
publica en esas fuentes un esquema propio completo de authorize/token, ejemplos
de token ITAD, ni un metodo preciso de autenticacion del cliente. La enumeracion
general de scopes omite `notifications`, aunque ambas rutas lo requieren.
Los campos/grants/errores siguientes proceden del estandar OAuth, no de una
nueva comprobacion real del servicio. La compatibilidad, metodo de autenticacion,
emision, expiracion y rotacion real son gates I3 pendientes. No se probaron con cuentas.

## Contratos y uso interno

`ItadClient` requiere `HttpTransport = (Request) => Promise<Response>`.
`list(accessToken)` y `waitlist(id, accessToken)` usan exclusivamente los GET
oficiales en `https://api.isthereanydeal.com`, Bearer en cabecera, validadores
existentes y comprobacion de identidad del detalle. No filtran `read`, no
registran IDs como entregados, no siguen Link ni deducen baseline.

`OAuthClient` requiere configuracion local y transporte. El metodo de
autenticacion es **explicito**, no autodetectado: `public`,
`client_secret_post` o `client_secret_basic` (estandar, a comprobar en I3).
No escoger `public` para una app con secreto emitido. Basic codifica cada
credencial como form antes de base64; post las incluye solo en el cuerpo.
No hay fallback de autenticacion ni reintento de codigos.

- Authorize: `response_type=code`, `client_id`, `redirect_uri`,
  `scope=notifications`, `state`, `code_challenge`, `code_challenge_method=S256`.
  State y verifier son aleatorios independientes de 256 bits, privados.
- Token: POST form `grant_type=authorization_code`, `code`, `redirect_uri`
  identico, `code_verifier` y autenticacion elegida.
- Refresh: POST form `grant_type=refresh_token`, `refresh_token` y la misma
  autenticacion. Scope se omite conforme a RFC 6749 seccion 6.
- Respuesta: `access_token` y `token_type` obligatorios; solo Bearer (case
  insensitive). `expires_in` opcional, entero no negativo; `scope` opcional
  hereda el solicitado/anterior y si viene debe contener `notifications`.
  `refresh_token` opcional; null/vacio no equivale a omision.
  Propiedades desconocidas se ignoran. No se impone longitud de JWT.
- Si refresh emite uno nuevo, reemplaza al anterior. Si lo omite, conserva
  el ultimo conforme a RFC 6749 seccion 6; no supone que sea permanente.
  Un fallo no instala tokens parcialmente validados. Si el servidor roto el
  refresh y se perdio/invalido la respuesta, conservar el antiguo NO garantiza
  recuperacion: puede requerir reautorizar. No hay entrega exactamente una vez.

`MemoryOAuthSession` mantiene tokens privados solo en memoria; no se serializa.
Entrega access valido sin red, al expirar comparte una renovacion concurrente
por instancia y reemplaza el conjunto validado atomicamente. Clear/install
impiden que una renovacion antigua resucite estado reemplazado.
`invalid_grant` en refresh limpia la sesion y exige reautorizacion; otros
errores se devuelven sin retry automatico. Un nuevo `accessToken()` despues
de un fallo es una solicitud explicita del caller, no backoff integrado.
La expiracion se calcula conservadoramente desde el inicio del POST.
Sin `expires_in`, la expiracion es **desconocida**, no una vida infinita
garantizada ni una fecha deducida del JWT; tras 401 el caller puede usar
`invalidateAccess()`. No hay reintento transparente de GET.

## HTTP y errores

Deadline fijo de 10 segundos incluye transporte y lectura del cuerpo.
Se aborta la solicitud y se limpia el timer en todas las salidas. Un transporte
simulado que ignore abort no bloquea el resultado; el adaptador real debera
respetar la cancelacion. Redirects rechazados para no reenviar credenciales.

`ServiceError` expone solo categoria fija y, cuando procede, status,
`retryAfterSeconds` y codigo OAuth de una lista permitida. Categorias:
configuration, input, timeout, network, http, rate_limit, json, shape, oauth,
state, expired, authorization_required. Sin `cause`, mensajes externos,
cuerpos, URLs ni secretos. JSON malformado se categoriza como json incluso en
un error HTTP de OAuth (status se conserva). Error OAuth desconocido queda
como oauth sin codigo externo; campo error mal formado se rechaza como shape.
No se captura silenciosamente un fallo como lista vacia o autorizacion exitosa.

429 usa solo Retry-After documentado (segundos o fecha HTTP). Sin cabecera
valida, demora desconocida; no inventa un valor ni toma `retry_after` del JSON
como contrato ITAD. No duerme ni reintenta automaticamente. El scheduling,
backoff durable y recuperacion quedan fuera de I2.

## Instrumento loopback temporal para preparar I3

`OAuthClient.begin()` crea `OAuthAttempt`. Solo admite callback HTTP exacto en
`127.0.0.1` con puerto explicito, sin query, fragmento o credenciales. La URL
de authorize se obtiene mediante `localAuthorizationUrl()` para handoff al
navegador **local**, nunca publicarla en chat/logs. No contiene tokens, codigo,
secreto ni verifier; state sigue siendo sensible.

`loopbackCallback(attempt, session)` es un handler Request/Response probado,
**no un servidor ni una CLI**. No hay comando para escuchar/iniciar OAuth real
en I2. No se implemento un adaptador Node/listener ni entrada de secretos:
eso se prepara tras permiso especifico I3, sin fingir readiness ahora.
El adaptador futuro debe enlazar solo 127.0.0.1, recibir secretos por entrada
local protegida (nunca chat, argumentos de CLI ni archivos versionados),
abrir authorize localmente sin imprimirlo, no registrar la URL callback que
contiene code/state y detenerse tras el resultado o timeout.

El handler valida metodo/origen/path, state unico y coincidencia antes del
POST. Un state correcto se consume sincronamente antes de intercambiar,
tambien ante denegacion, query invalida o fallo de token. Los estados
incorrectos no consumen el intento legitimo. TTL local 10 minutos y `cancel()`
borra state/verifier/URL. Respuestas fijas/sanitizadas, no-store y no-referrer;
sin endpoint status ni exposicion de tokens. No instala credenciales del
callback directamente: solo la respuesta validada del token endpoint.
No hay listener iniciado en este paso ni persistencia de tokens.

## QA reproducible, exclusivamente simulada

Desde la raiz:

```powershell
npm test -- tests/itad-client.test.ts tests/oauth.test.ts
npm run typecheck
npm test
```

Los dos archivos bloquean fetch global y verifican cero llamadas. Transporte
inyectado con Responses/streams, WebCrypto local, sin red ni cuentas.
Fixtures de lista/detalle reutilizan los ejemplos oficiales I1.
`oauth-token-rfc6749.json` reproduce RFC 6749 5.1 (token_type "example",
rechazado por este cliente; casos Bearer son derivados);
`oauth-error-rfc6749.json` reproduce el ejemplo de 5.2. Son ejemplos publicos
de estandar, no credenciales reales ni fixtures obtenidas de una cuenta.

Escenarios: rutas/cabeceras, listas vacias/shape invalida/detalle discrepante,
HTTP 400/401/403/404/5xx, network/JSON/stream, timeout transporte/cuerpo, 429,
PKCE vector RFC, state ausente/incorrecto/duplicado/replay/expirado/cancelado,
callback y denial sanitizados, token opcional/invalido/errores, expiracion,
rotacion/omision/invalid_grant, fallo parcial de refresh, concurrencia y clear.

Pendientes reales I3: autorizacion y metodo de cliente aceptado, renovacion
real usable tras expiracion, rotacion/revocacion y lectura con token renovado;
acordar almacenamiento protegido durable y concurrencia antes de I4.
Ninguna prueba mock sustituye esos gates. No solicitar datos reales en I2.
